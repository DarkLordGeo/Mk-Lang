# core-new benchmark rows

Rows of `tools/bench` (idiomatic standard library table) for functions of `std.core` and `std.mem`. Each row directory holds `bench.json`, the Mk package under `mk/`, and the baselines. Inputs are splitmix64 (Steele, Lea and Flood 2014) from the seed in the arguments, the same in every column; every program prints one checksum line folded with wrapping arithmetic. Only `tools/bench` publishes a number from these rows, with the machine alone.

## textmap

`TextMap.Set` and `TextMap.Replace` on overwrite-heavy churn. Per round: a fresh map; for `i` in `0..n`, `st += 0x9e3779b97f4a7c15`, the key is the decimal digits of `mix(st) % (n / 4 + 1)` (`mix` is splitmix64's finaliser), and the map sets it to `i`; then `st = seed ^ 0x5555555555555555` and for `i` in `0..n` the same key rule with a Replace to `i`, adding the old value to the sum, or 1 when the key was new. The round's value is the sum plus the final length; the total adds the rounds (seed + r) with wrapping. Usage: `textmap <n> <rounds> <seed>`.

Checksums (AMD Ryzen 7 9800X3D, Windows 11, 2026-11-11, each column built and run by hand, agreeing): quick `100000 3 1` gives `14895044761`, publish `2000000 3 1` gives `5958640198744` (Mk, Rust 1.99.1, Zig 0.17.0, Go 1.27.3).

Provisional timing, not a published number (AMD Ryzen 7 9800X3D, Windows 11, 2026-11-11 20:14, a shared machine; one run of each column at the publish size by `go run ./tools/bench verify -publish-size -mk <mk built from the tree at 20:13> -mk-std <the tree's std> core-new/chunks core-new/textmap`; the same command with other rows named gave every figure below marked 20:18 or 20:20): Mk 743 ms, Rust 975, Rust with overflow checks 1,136, Zig ReleaseFast 826, Zig ReleaseSafe 724, Go 1,454. Mk's ratio to Rust is about 0.76. That run had no `mk-keyed` column, which a map row needs; the run below has it.

The `mk-keyed` column (`TextMap.NewKeyed` under `HashKey.New`: SipHash-1-3 under a random per-process key, the DoS-resistant peer of Rust's `HashMap`) is the one Mk's ratio to Rust is quoted from. Provisional timing, not a published number (AMD Ryzen 7 9800X3D, Windows 11, 2026-11-11 21:00, a shared machine; one run of each column by `go run ./tools/bench verify -publish-size -mk <mk built from the tree at 20:54> -mk-std <the tree's std> core-new/chunks core-new/textmap core-new/deepfree`, which gives every figure below marked 21:00): Mk 616 ms, Mk keyed 603, Rust 828, Rust with overflow checks 868, Zig ReleaseFast 516, Zig ReleaseSafe 499, Go 913. Mk keyed's ratio to Rust is about 0.73; a second run (about 21:10, the same command with only this row named, after `verify` at the quick size, where every checksum agreed) gave Mk 669 ms, Mk keyed 632, Rust 959, Rust with overflow checks 819, Zig 540 and 586, Go 1,214, about 0.66; the keyed hash costs nothing measurable here (the two Mk columns are within one run's noise), a hypothesis, not profiled: the time may go to the key copies, the probes and the digit formatting more than to hashing keys of at most 6 bytes.

## chunks

`Slice.ChunksMut` and `Slice.Chunks` against each standard library's chunk iterator. `n` splitmix64 values (as in textmap, `st += 0x9e3779b97f4a7c15`, value `mix(st)`, from the seed) fill the slice once. Round `r` uses the piece length `k = (r % 16) * 4 + 1`: a mut pass sets each element of piece `j` (counted from 0) to `x * 3 + j`, then a shared pass adds, for each piece, its first element xor its last, and every element. The total adds the rounds' sums with wrapping. Usage: `chunks <n> <rounds> <seed>`. The mut pass iterates each piece's elements (Mk `for e in mut c`, Rust `iter_mut`); Go writes `c[i]` in a range over the piece's indices, whose bounds checks its compiler removes. C has no chunk iterator, and Zig's std has `std.mem.window`, which hands out const pieces only, so neither has a column: a hand-sliced mut pass would be a stand-in, which the idiomatic table refuses. Go uses `slices.Chunk` for both passes.

Checksums (AMD Ryzen 7 9800X3D, Windows 11, 2026-11-11, Mk, Rust 1.99.1, Zig 0.17.0, Go 1.27.3 each built and run by hand, agreeing): quick `65536 100 1` gives `14501135841921717839`, publish `65536 10000 1` gives `1252841694378895717`.

Provisional timing, not a published number (the same run, with a hand-sliced Zig column the row no longer has): Mk 350 ms, Rust 319, Rust with overflow checks 320, Zig ReleaseFast 317, Zig ReleaseSafe 353, Go 344. Mk's ratio to Rust is about 1.10, within the 1.25 bar. With the mut pass as `for e in mut c` and no Zig column (21:00, the same run as textmap's keyed figures): Mk 349 ms, Rust 314, Rust with overflow checks 317, Go 351, checksum unchanged; Mk's ratio to Rust is about 1.11.

## textset

`HeapText.Set` against each standard library's overwrite of a reusable string. A 4,096-byte source of lowercase letters (`mix(st) % 26 + 'a'`, `st` stepping from `seed ^ 0x5555555555555555`) is built once. Per round (seed + r): a fresh string; `n` times, `st += 0x9e3779b97f4a7c15`, `v = mix(st)`, `k = v % 300`, `off = (v >> 16) % 3796`, the string is set to `src[off..off + k]`, and the sum adds its length, `7 * first byte` and its last byte when it is not empty. The total adds the rounds' sums with wrapping. Usage: `textset <n> <rounds> <seed>`. Rust `clear` then `push_str`; Zig `ArrayList(u8)` `clearRetainingCapacity` then `appendSlice`; Go `append(b[:0], s...)`; C has no growable string.

Checksums (AMD Ryzen 7 9800X3D, Windows 11, 2026-11-11, Mk, Rust 1.99.1, Zig 0.17.0, Go 1.27.3 each built and run by hand, agreeing): quick `100000 3 1` gives `306659969`, publish `10000000 3 1` gives `30664548606`.

Provisional timing through `tools/bench verify -publish-size` (20:18, shared machine, one run per column, `10000000 3 1`): Mk 628 ms, Rust 347, Rust with overflow checks 348, Zig ReleaseFast 375, Zig ReleaseSafe 479, Go 272. Mk's ratio to Rust is about 1.81, over the 1.25 bar; the reason and the plan follow.

Earlier provisional timing (AMD Ryzen 7 9800X3D, Windows 11, a shared machine; `1000000 3 1`, wall clock by `date +%s%N`, three runs each): Mk 86 to 91 ms, Rust 58 to 63; a first single run also gave Zig 51 and Go 62. The same Mk program with only `Set` and `Len` in the loop took 88 to 90 ms, and with `s := src[off..off + k]` in place of `Set` 29 to 31 ms, so `Set` costs about 19 ns for an average of 150 bytes. `Set` is one compare and one `raw.Copy`, which reaches the support pack's `memcpy`: LLVM vectorizes its word loop, but its remainder is an 8-byte loop and a byte loop whose trip counts vary with the length (disassembled from a `-debug` build). The suspected cause is mispredicted loop exits on random lengths; the plan (size classes with overlapping head and tail copies) is not a std change.

`go run ./tools/bench verify -mk <mk built from the tree> -mk-std <the tree's std> core-new/chunks core-new/textset` (AMD Ryzen 7 9800X3D, Windows 11, 2026-11-11 18:09): both rows built all six columns (mk, rust, rust-ovf, zig-fast, zig-safe, go) and every quick checksum agreed. Its single quick runs are not published numbers (shared machine).

## sort

`Slice.Sort` against each standard library's unstable sort. Per round `r`: `n` values `mix(st)` with `st` stepping by `0x9e3779b97f4a7c15` from `seed + r * 0x5555555555555555`, sorted ascending; the round adds every 1,024th value times its index, and the last value. Usage: `sort <n> <rounds> <seed>`. C uses `qsort`, Rust `sort_unstable` (ipnsort), Zig `std.mem.sortUnstable` (pdqsort), Go `slices.Sort` (pdqsort).

Checksums (Mk, Rust, Zig, Go by hand, agreeing; all six columns and C again through `tools/bench verify`, 18:12): quick `100000 3 1` gives `13767744764125270723`, publish `1000000 10 1` gives `2194390077444048333`.

Provisional timing through `tools/bench verify -publish-size` (20:18, shared machine, one run per column, `1000000 10 1`): Mk 542 ms, C 829, Rust 110, Rust with overflow checks 110, Zig ReleaseFast 312, Zig ReleaseSafe 348, Go 556. Mk's ratio to Rust is about 4.9 (an earlier wall-clock run of `1000000 5 1` gave Mk 336 ms, Rust 107, Zig 219, Go 318). The reason, as far as it is known: `Sort` is a port of Go's `pdqsort_func` (its Hoare partition branches on every comparison, so random keys mispredict about half of them), and Mk matches Go's time; Rust's ipnsort partitions branch-free (a cyclic Lomuto partition) and sorts small slices with sorting networks. That does not explain the whole gap: Zig's `sortUnstable` is pdqsort too, and Mk takes about 1.74 times its ReleaseFast time and 1.56 times its ReleaseSafe time (which checks bounds as Mk does); no column was profiled to split the rest between bounds checks, the comparator call and the algorithm. ipnsort's partition is allowed (oracle: sorted, a permutation, evaluator equals native); the port must bring `TestSortMatchesGo` (std/regress_test.go), which pins Go's permutation, with it. The plan: profile Mk against Zig on this row first, then port ipnsort's partition and small sorts with a differential Go test against `slices.Sort` on distinct keys and the adversarial comparators of tests_list.mk.

## sortstable

`Slice.SortStable` against each standard library's stable sort. Records `(key: u32, id: u32)`, key `mix(st) % 1000` (seeds as in sort), id the index, sorted by key; the round adds every 1,024th id times its index, and the last record's `key * 1000003 + id`. Usage: `sortstable <n> <rounds> <seed>`. C has no stable sort.

Checksums (Mk, Rust, Zig, Go by hand, agreeing): quick `100000 3 1` gives `730243003728`, publish `1000000 10 1` gives `2440905276202704`.

Provisional timing through `tools/bench verify -publish-size` (20:18, shared machine, one run per column, `1000000 10 1`): Mk 1,318 ms, Rust 71, Rust with overflow checks 69, Zig ReleaseFast 470, Zig ReleaseSafe 510, Go 1,274. Mk's ratio to Rust is about 18.6 (an earlier wall-clock run of `1000000 5 1` gave Mk 740 ms, Rust 70, Zig 296, Go 732). Mk matches Go (the same algorithm, in place, O(n log² n) moves); Zig's in-place block sort is about 2.8 times faster, and Rust's driftsort, which allocates a scratch buffer, far more. `SortStable` takes no allocator, so the scratch-buffer merge Rust uses is out of reach without a signature change. An allocating variant is a roadmap item.

## deepfree

Build, read and release a list of owned strings: an allocator benchmark with the deep `Free` on top. It does not isolate `Free`: `HeapList[HeapText].Free` releases every text, then the storage, but the timed region is mostly the n allocations and copies. The 4,096-byte source is textset's. Per round (seed + r): a fresh list; `n` times, `st += 0x9e3779b97f4a7c15`, `v = mix(st)`, `k = v % 64`, `off = (v >> 16) % 4032`, a heap copy of `src[off..off + k]` is appended; one pass adds each string's length, `7 * first byte` and its last byte when it is not empty; then the list is released. The total adds the rounds' sums with wrapping. Usage: `deepfree <n> <rounds> <seed>`. Rust drops a `Vec<String>`; Zig frees each string of a `std.ArrayList([]u8)` and deinits it; C frees each `malloc` copy and the `realloc`-grown array. Go has no column: it drops a `[]string` and its collector frees it, so there is no release walk to time. The timed region is the whole program, so every column includes building the list and the read pass. Like Mk, Rust and Zig, C allocates no block for an empty string (it keeps a null pointer).

Provisional timing, with no Go column and no C allocation for an empty string (21:00, the same run as textmap's keyed figures; checksum unchanged): Mk 211 ms, C 264, Rust 279, Rust with overflow checks 365, Zig ReleaseFast 121, Zig ReleaseSafe 174.

Checksums (Mk and Go by hand; seven columns, a Go column among them, through `tools/bench verify`, 20:19, agreeing): quick `100000 3 1` gives `267884541`, publish `1000000 5 1` gives `4466063722`.

Earlier provisional timing, with a Go column and C allocating empty strings (`tools/bench verify -publish-size`, 20:20, shared machine, one run per column): Mk 216 ms, C 273, Rust 297, Rust with overflow checks 298, Zig ReleaseFast 113, Zig ReleaseSafe 171, Go 264. Zig's lead is probably its allocator (`std.heap.smp_allocator`, built for many small blocks) rather than the release walk, a hypothesis: no column was profiled to split the time. This ratio is not a measure of `Free`, and the audit table quotes none for it.
