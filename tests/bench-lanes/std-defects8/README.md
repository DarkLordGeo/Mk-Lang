# std-defects8 benchmark rows

Rows for the std speed bar: a std function measured more than 2 times slower than the best of C, Rust, Zig and Go is a defect to close, with a row here. Published numbers come only from `go run ./tools/bench publish std-defects8/<row>`, with the machine alone; the numbers below say who measured them and how. **No row here is published yet, so the bar is not yet shown met for any of them.**

## sort

`Slice.Sort` against each standard library's unstable sort: the task, the sources of the other columns and the checksums of `core-new/sort` (tests/bench-lanes/core-new/README.md, "sort"), so this row and that one compare Mk's Sort after and before the change. Per round `r`: `n` values `mix(st)` with `st` stepping by `0x9e3779b97f4a7c15` from `seed + r * 0x5555555555555555`, sorted ascending; the round adds every 1,024th value times its index, and the last value. Usage: `sort <n> <rounds> <seed>`; quick `100000 3 1` gives `13767744764125270723` (core-new's quick size, so the two rows compare there), publish `10000000 1 1` gives `5816766227949892082`: the contract's 10 M keys, one round, where core-new publishes ten rounds of 1,000,000 (`2194390077444048333`), whose 8 MB of keys stay in the publish machine's 96 MB L3.

What changed (std/core/core_sort.mk): an element of at most 32 bytes is partitioned by ipnsort's branch-free cyclic Lomuto partition (`PdqPartitionLomuto`), so the comparison's result feeds no branch, unless the range's pivot sample reads increasing, where Go's Hoare partition keeps an ordered range in order (see below); the rest of the sort is still Go's pdqsort_func. The Go model `mkSortModel` (std/std-defects_sortmodel_test.go) makes the same calls of `less` and the same moves, and `TestStdColl_SortAdversarialMatchesGo`, `TestStdColl_EvalParity` and `TestStdDefects_SortElementSizes` check Mk against it (comparison counts, permutations, evaluator against native). `TestNearlySortedWithinGo` and `TestSortCountsWithinGo` bound the model's comparisons at 1.25 times Go's own `sort.Slice` on every pattern of `sortCases` and on sorted input with 10, 100 and 1,000 swaps at n = 1,000,000.

**Nearly sorted input.** With the Lomuto partition taken on every range, nearly sorted input costs about 3 times Go's comparisons: measured with the Go model (the counts are deterministic; machine immaterial), n = 1,000,000, 8-byte elements, sorted plus 10, 100 and 1,000 random swaps: 14.06n, 35.45n and 31.17n calls of less against Go's 9.47n, 10.90n and 14.91n. With the pivot-sample check: 9.47n, 10.90n and 14.99n; random input 21.33n against Go's 21.12n, the same with and without it.

Earlier provisional numbers (core-new's README, `tools/bench verify -publish-size`, shared machine): Mk 542 ms, Rust 110, Zig ReleaseFast 312, Go 556, C 829.

Hand timings on 2026-11-13 (AMD Ryzen 7 9800X3D, Windows 11, other work running; wall clock of one process each, `1000000 10 1`; not through tools/bench): Mk's release build before the Lomuto change 802, 589, 595 ms, after it 248, 222, 211 ms; Rust's `sort.rs` built with `rustc -C opt-level=3` only (not the contract's flags) 129, 124, 122 ms. These runs are outside the benchmark contract (the contract's Rust flags, hyperfine with at least 10 runs, nothing else running), so they show no ratio. Whether Sort meets the bar is the publish step's to show: `go run ./tools/bench publish std-defects8/sort` with the machine alone, not yet run.

## sortstr

`Slice.Sort` over strings, the other half of the contract's `sort` row ("std sort of 10 M `u64` and of strings"), which the `sort` row leaves out. Per round `r` each key is the 16 lowercase hex digits of the `sort` row's value, in one buffer, and each column sorts views of that buffer by byte order (Mk `str` with `<`, Rust `&str` with `sort_unstable`, Zig `[]const u8` with `std.mem.sortUnstable` and `std.mem.lessThan`, Go substrings with `slices.Sort`, C pointers with `qsort` and `strcmp`); no column allocates per key. The fold reads every 1,024th key back as a number, so the checksums are the `sort` row's: quick `100000 3 1` gives `13767744764125270723`, publish `10000000 1 1` gives `5816766227949892082` (Go column, 2026-11-13; the contract's 10 M). `str` is 16 bytes, so Mk's Sort takes the Lomuto partition here, with a comparator that compares bytes. Not published.

## fs

A copy of `std-fs2/fs` (its sources but for the tree's name, `mkbench-sd8-<language>`, so the two rows never share a tree; the `copy` variant left out; a duplicate by task, so only one of the two is to be published), for two functions over the bar: `fs.Walk` on Windows at about 3 times Rust and Zig, and `RemoveAll` at about 2.5 times Rust, both from hand timings and a one-shot verify run on a loaded machine, so provisional. The causes, read from the code: on Windows each directory costs three blocking-pool jobs (`rt.DirOpenAt`, the first `DirFill`, the fill that finds the end), and `RemoveAll` one pool job per entry; on Linux every listed entry costs a `statx` that getdents64's `d_type` makes unneeded for `Walk` and `RemoveAll`. The Windows half is in: where `sys.DirFillOnOpen` is true (std/sys/windows/dir.mk), `rt.DirOpenAt` (std/rt/removeat.mk) makes the stream's first `DirFill` in the open's own pool job, so a directory costs two pool hops, not three; its effect is not shown (a hand A/B on the loaded machine showed nothing either way). Not made yet: the Linux kind-only listing (`d_type`, `statx` only on `DT_UNKNOWN`), a Windows stream ended without the extra fill, and `RemoveAll`'s one pool job per entry. Not published.

## sortstable

`Slice.SortStable` against each standard library's stable sort: the task, the sources of the other columns and the checksums of `core-new/sortstable` (tests/bench-lanes/core-new/README.md, "sortstable"). Records `(key: u32, id: u32)`, key `mix(st) % 1000`, id the index, sorted by key; quick `100000 3 1` gives `730243003728`, publish `1000000 10 1` gives `2440905276202704`. C has no stable sort.

This row records the bar's one stated exception: `SortStable` stays in place with no allocation, because a std sort that takes heap memory unseen is wrong for code with no heap or inside a handler. Every stable sort near Rust's driftsort merges through a scratch buffer of up to n elements; Go's `slices.SortStableFunc` is the same in-place algorithm as Mk's and as slow, and Zig's in-place block sort is the fastest in-place column. A `SortStableIn(a, ...)` with an allocator is a roadmap item. Nothing in std/core changed for this row. The exception covers every column, the in-place ones included: Zig's block sort (WikiSort-style) is O(n log n) moves where Mk's SymMerge is O(n log² n), and an in-place block merge with no allocation is a roadmap item. The row records both ratios, against the best column (driftsort) and against the best in-place column (Zig's `std.mem.sort`), once `tools/bench publish` gives them; no ratio is recorded here until then.

Earlier provisional numbers (core-new's README, `tools/bench verify -publish-size`, shared machine, one run per column): Mk 1,318 ms, Rust 71, Zig ReleaseFast 470, Go 1,274: Mk about 18.6 times Rust and 2.8 times Zig. The published ratio is the publish step's (`go run ./tools/bench publish std-defects8/sortstable`, with the machine alone).
